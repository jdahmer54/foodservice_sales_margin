# Staffing Operations SML Model

AtScale SML repository generated by the atscale-sml-model-generator skill from a staffing-ops
demo-data bundle (a travel-nurse / allied-health staffing agency order-to-cash dataset). Logical
model names are genericized per Rule 18 — any customer-identifying name appears only in
`context/` (the verbatim inputs) and, where the DDL requires it, in physical connection values
(Rule 17's exception; here the schema name `se_library` is generic, not customer-specific, so no
retained reference was needed).

## Inputs

- **Use case document** (`context/use_case.md`) — scenario, six subject areas, 15 engineered
  narratives, the 16-table grain description, aggregate shape, and known limitations.
- **NLQs** (embedded in `use_case.md`, and also provided standalone as
  `context/nlq_smoke_tests.sql` — one runnable SQL query per brief NLQ) — 21 locked
  natural-language questions across the six subject areas.
- **DDL** (`context/ddl.sql`, from `databricks/02_ddl.sql`) — Databricks/Unity Catalog
  `CREATE OR REPLACE TABLE` statements for all 16 tables. Treated as authoritative; the
  physical schema was not redesigned.
- **Data profile** (`context/data_profile.yaml`) — column-level profile (type, nullability,
  description, sample values, min/max, additivity) for all 16 tables, used for `is_unique_key`
  derivation (Rule 16) and additivity/format decisions.
- **ERD** (`context/erd.mmd`) — Mermaid `erDiagram` confirming relationships and cardinality,
  including the `fact_placement` self-reference on `previous_placement_id`.
- **Manifest** (`context/manifest.json`) — machine-readable bundle summary (row counts, window
  dates, warehouse target, use cases covered/excluded).
- **Original bundle archive** (see `context/` for the verbatim zip file) — the archive the
  caller supplied, containing all of the above plus the generator scripts and CSVs.
- **Live database access via MCP** — not provided; the data profile YAML was used instead
  (`references/data-profile.md` "pick exactly one per run").
- **Existing SML files** — not provided; this is a new model, not an extension.
- **`build.yaml`** — not provided by the caller. All build parameters below were derived from
  the inputs or the skill's documented defaults; see "Assumptions and decisions".

## Build parameters

- **warehouse**: Databricks (Unity Catalog)
- **model_unique_name**: `staffing_ops`
- **catalog_unique_name**: `staffing_ops_catalog`
- **currency**: USD
- **time_window**: calendar (no fiscal/retail445 markers in the use case)
- **unrelated_dimension_handling**: `repeat` (skill default; this is a multi-fact model)
- **use_cases_covered**: all six — order-to-fill velocity; bill/pay margin integrity; clinician
  retention, extension & redeployment; credentialing/start-date risk; recruiter & sales
  productivity; rate competitiveness & demand forecasting
- **use_cases_excluded**: payroll/timesheet processing detail; candidate sourcing/marketing
  funnel (both out of scope in the source bundle itself — different grain, no tables provided)
- **semi_additive_default**: none required — no snapshot/balance-style fact needed
  `semi_additive:` in this model (see "Assumptions and decisions" on `fact_rate_benchmark`)

## Assumptions and decisions

- **warehouse = Databricks** — the DDL uses `CREATE OR REPLACE TABLE` with backtick-quoted,
  loader-substituted catalog/schema placeholders and Unity-Catalog-style `CLUSTER BY`, and all
  identifiers in the DDL are lowercase — both are Databricks/Unity Catalog signatures
  (`manifest.json` also states `"warehouse": "databricks"` explicitly).
- **database = main, schema = se_library** — the DDL parameterizes catalog/schema as loader
  variables substituted by the bundle's own `load.sh` at load time; per Rule 17 an
  unresolved placeholder cannot be emitted into the connection. `manifest.json` records that the
  schema (`se_library`) WAS explicitly SE-provided and the catalog (`main`) was the bundle's own
  default, not confirmed by the SE — `main` was kept as the concrete default since Databricks
  conventionally uses `main` as its default catalog. Whoever loads this model into a different
  workspace should update `connections/Staffing Ops Connection.yml`'s `database:` to match.
- **model_unique_name = staffing_ops / catalog_unique_name = staffing_ops_catalog** — genericized
  from the use case per Rule 18 (never bake the customer name into logical metadata); `_catalog`
  suffix per Rule 8c.
- **currency = USD** — all rates in the use case and DDL are explicitly USD/hr.
- **time_window = calendar** — no fiscal-year or 4-4-5 retail calendar signal anywhere in the use
  case; a plain Gregorian Year > Quarter > Month > Day hierarchy was used (Date Dimension does
  not need the Custom PP445 / Retail445 machinery the Internet Sales reference bundles, since
  nothing here needs a non-calendar fiscal year).
- **unrelated_dimension_handling = repeat** — no `build.yaml` was supplied; this is the skill's
  documented default and the safest choice for ad-hoc BI tools (Rule 3). Applied to every base
  metric.
- **fact_placement.previous_placement_id (self-reference) is NOT modeled as a dimension
  relationship or snowflake.** A snowflake relationship must be intra-dimension (Rule 5) and this
  is a fact-to-itself chain (extension legs), which SML has no first-class construct for. The
  extension chain is instead exposed through two already-baked-in fact columns —
  `is_extension` / `extension_sequence_number` (base metric `Extension_Count`, calc
  `Extension_Rate`) and `has_next_assignment_booked` / `gap_days_to_next_assignment` (base
  metrics `No_Next_Assignment_Count`, `Avg_Gap_Days_To_Next_Assignment`) — which answer the
  retention/redeployment NLQs without needing to walk the self-referencing key at query time.
- **fact_credential_item carries none of specialty_id / facility_id / client_id / recruiter_id /
  msp_program_id** needed to answer "by state and specialty" / "by client" (NLQs 4.2, 4.3). Per
  Rule 15, a query dataset (`fact_credential_item_enriched`) joins fact_credential_item to
  fact_placement to bring those columns in; all credentialing metrics are defined on the
  enriched dataset. The raw `fact_credential_item` dataset is still emitted (documents the
  physical table per the DDL) but is intentionally left unattached to the model — nothing
  references it directly, so Rule 20 does not apply to it.
- **"Zero-submission open orders" (NLQ 1.2) requires a per-requisition anti-join count** (zero
  matching rows in fact_submission) that a snowflake relationship cannot express (Rule 5 requires
  many-to-one; this is a one-to-zero/many aggregation). Per Rule 15, a second query dataset
  (`vw_requisition_submission_summary`) pre-aggregates a `submission_count` per requisition via
  `LEFT JOIN ... GROUP BY`, and bakes the exact NLQ condition (status = Open, age > 21 days, zero
  submissions) into a single flag column, exposed as `Stale_Zero_Submission_Open_Order_Count`.
- **Recruiter Dimension is snowflaked across dim_recruiter_team and dim_recruiter as ONE
  dimension** (Team > Recruiter), per Rule 5 — the two tables back one logical hierarchy rather
  than two separate dimensions linked by an inter-dim snowflake (which AtScale rejects at load).
- **Facility Dimension embeds Market Dimension** (`type: embedded`, joined on `market_id`) so that
  `fact_placement` — which carries `facility_id` but no `market_id` of its own — can still be
  sliced by Region/Division/MSA for the market-erosion NLQ (2.3), mirroring the Internet Sales
  `Customer Dimension` -> `Geography Dimension` embedded pattern.
- **`dim_clinician` is attached to the model as a fact** (relationship to Specialty Dimension on
  `primary_specialty_id`) purely so its `Available_Compliant_Clinician_Count` measure can be
  sliced by specialty (Rule 20 — a metric's dataset must appear as a `from.dataset` in some model
  relationship, or AtScale renders it unattached).
- **`fact_rate_benchmark.month_id` joins directly to `Date Dimension` at the `Day` level** — its
  values are literal `YYYYMM01` date keys (the profile confirms they fall inside `dim_date`'s
  `date_id` domain, always the first of a month), so no separate month-grain bridge dimension is
  needed; Day rolls up to Month/Quarter/Year in the same conformed hierarchy. No `semi_additive`
  block was needed since nothing on this fact is a snapshot balance to be held constant across
  time — `order_volume` / `filled_count` are additive, and the rate columns are ordinary averages.
- **Every fact's primary event date is conformed, unprefixed, to the single plain `Date
  Dimension`** (Rule 21): `fact_requisition.posted_date`, `fact_placement.start_date`,
  `fact_credential_item_enriched.due_date`, `fact_rate_benchmark.month_id`, and
  `fact_submission.submission_date` all join the same dimension with no `role_play`, so
  cross-fact ratios (e.g. Order Volume vs. Placement Count trends) share one time axis.
  `role_play` is reserved for the genuine second-date case on a single fact:
  `fact_placement.scheduled_end_date` ("Scheduled End {0}"),
  `fact_placement.actual_end_date` ("Actual End {0}"), and
  `fact_credential_item_enriched.completed_date` ("Completed {0}").
- **14/30/45-day "next N days" NLQs (3.1, 3.3, 4.1) are answered with a live relative-date filter
  on the appropriate Date Dimension relationship** (e.g. `Scheduled End Day` between "today" and
  "today + 30"), not a baked static flag — the bundle's synthetic "today" (2026-09-17) is a data
  calibration anchor, not something the semantic model should hard-code. `age_days_as_of_current`
  and `gap_days_to_next_assignment`, by contrast, are pre-computed data columns (not model-layer
  literals), so metrics built directly on them (`Avg_Age_Days_Open`,
  `Avg_Gap_Days_To_Next_Assignment`) are fine as-is.
- **`is_below_target_margin_flag` bakes in the use case's own stated $15/hr target margin**
  (narrative #5) as a calculated column on `fact_placement`, since the use case names a specific,
  fixed threshold rather than a value that varies by context.
- **`PrevMember` (adjacent-period, for QoQ) and `ParallelPeriod` (same-period-prior-year, for YoY,
  per Rule 13)** are both used as dot-accessed member functions (`<Member>.PrevMember`, no
  parentheses) consistent with `CurrentMember`'s usage in the bundled Internet Sales calcs; no
  bundled example demonstrates `PrevMember` specifically, so this follows standard MDX member-
  function syntax rather than a cited example — flagged here per the grounding doctrine.
- **`Gross_Profit` is an approximation** (`gross_margin_hourly x weekly_hours x 13`, i.e. a
  13-week/one-quarter run-rate), mirroring the same approximation already baked into
  `nlq_smoke_tests.sql`'s NLQ 5.1/5.3 answers — there is no separate invoiced-hours fact in this
  bundle (see use case "Known limitations": no timesheet/invoice-grain data).

## Generation summary

- **Datasets**: 18 (11 dimension tables, 5 fact tables, 2 query datasets bridging
  indirect joins per Rule 15: `vw_requisition_submission_summary`,
  `fact_credential_item_enriched`)
- **Dimensions**: 12 (9 standard dimensions, 1 time dimension, 2 degenerate
  dimensions: Requisition Status, Assignment Status)
- **Snowflake dimensions**: 1 — Recruiter Dimension (dim_recruiter_team -> dim_recruiter)
- **Embedded dimension relationships**: 1 — Facility Dimension -> Market Dimension
- **Base metrics**: 31
- **Calculated metrics**: 20 (12 ratio/gap calcs, 4 year-over-year calcs using
  ParallelPeriod, 4 quarter-over-quarter calcs using PrevMember)
- **Model relationships**: 36
- **Role-play prefixes**: `Scheduled End {0}`, `Actual End {0}` (both on `fact_placement`),
  `Completed {0}` (on `fact_credential_item_enriched`) — all against the single conformed
  `Date Dimension`
- **Calculated (derived) columns added**: `prior_year_num` (dim_date); `is_filled_flag`,
  `is_open_flag`, `is_cancelled_flag` (fact_requisition); `is_offer_extended_flag`,
  `is_placed_flag` (fact_submission); `is_extension_flag`, `is_fall_off_flag_num`,
  `is_below_target_margin_flag`, `no_next_assignment_flag`, `gross_profit_amount`
  (fact_placement); `is_available_compliant_flag` (dim_clinician); `submission_count`,
  `zero_submission_flag`, `stale_zero_submission_open_flag` (query dataset); `is_compliant_flag`,
  `is_outstanding_flag`, `delayed_start_flag` (query dataset)
- **Caveats**: `fact_requisition.filled_date` / `cancelled_date` and
  `fact_credential_item_enriched.status` (Pending/Submitted/Approved/Rejected) are not modeled as
  separate dimension relationships or role-plays — no NLQ requires trending or slicing by them
  specifically, and they remain queryable as plain dataset columns if a future need arises. The
  self-referencing `previous_placement_id` extension chain is not walkable via MDX (see
  "Assumptions and decisions"); a use case that needed to browse the literal chain (not just its
  rate/gap outcomes) would need a recursive query dataset, which was judged out of scope here
  since `Extension_Count` / `Extension_Rate` / `Avg_Gap_Days_To_Next_Assignment` already answer
  every locked NLQ that touches extensions and redeployment.

## Reproducing this build

`context/` holds verbatim copies of every input consumed for this build — `use_case.md`,
`erd.mmd`, `data_profile.yaml`, `ddl.sql`, `manifest.json`, `nlq_smoke_tests.sql`, and the
original bundle archive itself. No `build.yaml` was supplied, so re-running the
atscale-sml-model-generator skill against this same `context/` folder (or the original bundle)
with the same derivation rules — Databricks warehouse, `main`/`se_library` connection, `repeat`
for unrelated_dimensions_handling, calendar time window — should reproduce an equivalent model.
